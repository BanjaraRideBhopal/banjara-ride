## 1. Goal

Give the owner a single super_admin-only page to log business-wide expenses and income, and see a monthly profit figure (vendor earnings + subsidy + other income − expenses) alongside supporting charts.

## 2. Scope

**In scope:**
- New `expense_categories` lookup table (8 seed rows, admin-extensible via inline "+ Add new category..." — mirrors `VehicleMaster.js`'s `__new__` sentinel pattern)
- New `expenses` table (category, amount, date, optional description) — **no `centre_id` column** (category names already encode centre scope where relevant; owner decision, final)
- New `income_records` table covering both govt subsidy and other income, distinguished by `income_type` (`'subsidy'` | `'other'`) — no vehicle linkage (subsidy is a lump sum per month, not per-vehicle; owner decision, final)
- New `src/pages/Accounts.js`, super_admin only, with a single-month picker (`<input type="month">`, same as `VendorPayouts.js`)
- Expense entry form + table of this month's expenses, with inline edit and super_admin delete (§9)
- Income entry form + table of this month's income, with inline edit and super_admin delete (§9)
- Profit summary panel for the selected month: `BJ Earn (sum) + Govt Subsidy (sum) + Other Income (sum) − All Expenses (sum)`
- 5 required charts/tables (§6)
- A small shared util, `src/utils/vendorRevenue.js`, extracting the exact BJ Earn / Owner Amt formula out of `VendorPayouts.js` so this is its second consumer, not a duplicate (Ponytail — reuse, don't re-derive)
- New nav link "Accounts" in `BookingSheet.js` header, super_admin only, same pattern as Dashboard/Vehicles/Vendor Payouts
- New `activePage === 'accounts'` routing in `App.js`, gated `profile.role === 'super_admin'`
- RLS on `expenses` and `income_records` that is **stricter than every other table in this app** — see §5

**Out of scope (explicitly, do not build):**
- A 9th "Maintenance" expense category or any new maintenance data-entry UI — maintenance chart data (§6 item 1) reads the **existing** `maintenance_expenses` table (Phase 11) read-only
- `centre_id` on `expenses` or `income_records`
- Vehicle linkage on `income_records` (subsidy/other income is never tied to a specific vehicle)
- Renaming or deleting `expense_categories` rows (add-only, like `vehicle_types`)
- Any DDL change for delete — §4.2/§4.3's `FOR ALL` RLS policy already permits it; delete is a UI-only addition (§9)
- Any change to `VendorPayouts.js`'s UI, formula, or output — the only touch to that file is the mechanical extraction in §4.4

### 4.4 Extract shared vendor-revenue helper (code change, not SQL — listed here because it must land before `Accounts.js` can use it)

**Why:** `Accounts.js` needs the exact same BJ Earn / Owner Amt formula `VendorPayouts.js` already computes (`computeRow()`, `src/pages/VendorPayouts.js` lines 68–86 as of this spec). This is the second consumer of that formula, which is this project's Ponytail threshold for extracting a shared helper instead of duplicating it — confirmed genuinely identical by reading the live source, not assumed.

**Create `src/utils/vendorRevenue.js`:**

```js
// Shared vendor revenue-share calculation — extracted from VendorPayouts.js (Phase 15)
// so Phase 16 (Accounts.js) can reuse the exact same BJ Earn / Owner Amt formula
// instead of duplicating it a second time.

export function buildCreditByReg(bookings) {
  const creditByReg = {};
  bookings.forEach(b => {
    creditByReg[b.vehicle_number] = (creditByReg[b.vehicle_number] || 0) + (parseFloat(b.final_rent) || 0);
  });
  return creditByReg;
}

export function buildMaintenanceByVehicleId(expenses) {
  const maintenanceByVehicleId = {};
  expenses.forEach(e => {
    maintenanceByVehicleId[e.vehicle_id] = (maintenanceByVehicleId[e.vehicle_id] || 0) + (parseFloat(e.amount) || 0);
  });
  return maintenanceByVehicleId;
}

export function computeVendorRow(vv, creditByReg, maintenanceByVehicleId) {
  const reg = vv.vehicles.registration_number;
  const credit = creditByReg[reg] || 0;
  const gst = credit * 0.06;
  const creditAfterGst = credit - gst;
  const parking = parseFloat(vv.parking_charge) || 0;
  const maintenance = maintenanceByVehicleId[vv.vehicle_id] || 0;
  const amountLeft = creditAfterGst - parking - maintenance;
  const pct = parseFloat(vv.owner_share_pct) || 0;
  const ownerAmt = amountLeft * pct;
  const bjEarn = amountLeft - ownerAmt;
  return { credit, gst, creditAfterGst, parking, maintenance, amountLeft, pct, ownerAmt, bjEarn };
}
```

**Modify `src/pages/VendorPayouts.js`:**
- Add `import { buildCreditByReg, buildMaintenanceByVehicleId, computeVendorRow } from '../utils/vendorRevenue';`
- Delete the local `creditByReg` / `maintenanceByVehicleId` object-building code and the local `computeRow` function (current lines ~68–86)
- Replace with:
  ```js
  const creditByReg = buildCreditByReg(bookings);
  const maintenanceByVehicleId = buildMaintenanceByVehicleId(expenses);
  function computeRow(vv) { return computeVendorRow(vv, creditByReg, maintenanceByVehicleId); }
  ```
- Everything else in the file (all existing `computeRow(vv)` call sites, the statement table, vendor management) is unchanged — this is a mechanical extraction with zero behaviour change. Run `npm run build` and spot-check the statement table against pre-change numbers for the current month before considering this step done.

## 5. RLS — explicit deviation from this app's usual pattern (owner-decided, final)

Every other admin-only page in this app (`VendorPayouts.js`, `VehicleMaster.js`'s Rate Cards, `Dashboard.js`'s source tables) uses RLS that lets **any authenticated user** read the underlying table via a direct Supabase API call — the admin-only **page** is what hides it in the UI, the database does not. `vendors`, `vendor_vehicles`, `rate_groups`, `vehicle_type_rates` all follow this "read_all + super_admin_write" shape.

The owner explicitly decided that shape is **not acceptable** for `expenses` and `income_records`, given the sensitivity of HR/salary and other financial line items — staff must not be able to read this data even by calling the Supabase API directly with their own staff credentials, bypassing the UI entirely.

Concretely: both tables get exactly one RLS policy each, `FOR ALL` scoped to `is_super_admin()`, and **no other policy** — there is no `read_all` policy on either table. `expense_categories` is explicitly exempted from this and keeps the normal "read_all + super_admin_write" shape, since it only ever holds category names, never amounts (owner-confirmed, §4.1).

## 6. Charts / Tables (§6.1–§6.5) — formula clarifications

All 5 items read from tables/formulas that already exist elsewhere in this app (§6.1 from `maintenance_expenses`, §6.2/§6.5 from the Phase 15 formula, §6.3/§6.4 from this phase's own new tables) — none of them are new raw data.

**Correction to the raw requirement:** the owner's note for item 2 lists `vehicle_type_rates` as a table this calculation reads. Reading the live `VendorPayouts.js` source (confirmed in §4.4), `computeRow()` does **not** touch `vehicle_type_rates` at all — it only reads `bookings.final_rent`, `vendor_vehicles.parking_charge`/`owner_share_pct`, and `maintenance_expenses.amount`. The spec below follows the actual code, not the raw requirement's table list.

1. **Maintenance per month** — read-only from `maintenance_expenses`, **not** a new category. Line chart, trailing 6 months ending at the selected month (§9).
2. **Rent paid to the vendor per month** — `Owner Amt` summed across all active `vendor_vehicles`, using `computeVendorRow()` from §4.4. Line chart, same trailing 6-month window as item 1.
3. **Each expense category per month** — breakdown of the new `expenses` table grouped by `category_id`, for the **single selected month** only (not a trend — a category already gives multiple bars within one month). Bar chart.
4. **Govt subsidy per month** — from `income_records` where `income_type = 'subsidy'`. Line chart, same trailing 6-month window as items 1–2.
5. **Per-vehicle earn** — `BJ Earn` per individual vehicle (not summed), using `computeVendorRow()` from §4.4, for the **single selected month** only. Rendered as a **plain sortable table** (not a chart — 57 vehicles is too many bars to read), sorted descending by BJ Earn: Vehicle Type, Reg. No., Vendor, BJ Earn ₹.

All five choices (window length, chart type per item, item 5's table-not-chart rendering) are confirmed in §9.

### 6.6 Computing the multi-month trend (items 1, 2, 4)

For a trailing window of 6 months ending at the selected month:
1. Compute the 6 month boundaries (first/last day of each) the same way `VendorPayouts.js`'s `monthRange()` does, one per month in the window.
2. Item 1 (maintenance): one query — `maintenance_expenses` filtered `expense_date` across the whole window — then group the results by `YYYY-MM` of `expense_date` client-side.
3. Item 2 (vendor rent / Owner Amt): one query each for `bookings` (`status='end'`, date across the whole window) and `maintenance_expenses` (same window) plus the existing `vendor_vehicles` fetch. For each of the 6 months, build that month's `creditByReg`/`maintenanceByVehicleId` via `buildCreditByReg`/`buildMaintenanceByVehicleId` (§4.4) using only that month's slice of the fetched rows, run `computeVendorRow()` per active `vendor_vehicles` row, and sum `ownerAmt` across all of them → one point per month.
4. Item 4 (subsidy): one query — `income_records` where `income_type='subsidy'` across the whole window — grouped by `YYYY-MM` of `income_date`.

### 6.7 Single-month breakdowns (items 3, 5)

- Item 3: `expenses` filtered to the selected month's date range, grouped by `category_id` → `expense_categories.name`, summed `amount`.
- Item 5: reuse the exact same `activeVV` / `computeVendorRow()` pass `VendorPayouts.js`'s statement table does for the selected month, but read off `.bjEarn` per row instead of grouping by vendor — one table row per vehicle, sorted descending by `bjEarn`.

### 7.1 Why not `.desktop-table`

`VendorPayouts.js`'s Phase-15 post-ship fix documents a real bug: `.desktop-table`'s sticky-header CSS is coupled to `BookingSheet.js`'s two-row `<thead>` shape, and reusing it on a single-header-row table pushed the header down and visually covered the row underneath. `Accounts.js`'s expense/income tables have a single header row, so — per that fix and per the owner's explicit instruction — they must use plain `overflowX: 'auto'` wrapping (the pattern `VendorPayouts.js` now uses, and that `VehicleMaster.js` already used), never `.desktop-table`.

## 8. Profit Formula (exact)

For the selected month:

```
BJ Earn (sum)     = Σ computeVendorRow(vv).bjEarn, for every active vendor_vehicles row, using that
                    month's bookings (status='end') and maintenance_expenses (§4.4/§6.7)
Govt Subsidy (sum) = Σ income_records.amount WHERE income_type = 'subsidy' AND income_date in month
Other Income (sum) = Σ income_records.amount WHERE income_type = 'other'   AND income_date in month
All Expenses (sum)  = Σ expenses.amount WHERE expense_date in month

Profit = BJ Earn (sum) + Govt Subsidy (sum) + Other Income (sum) − All Expenses (sum)
```
